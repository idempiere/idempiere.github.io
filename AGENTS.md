# AGENTS.md

This file provides guidance to AI coding agents (Claude Code, Gemini CLI, Qwen Code, Codex, OpenCode, and others) when working in this repository.

## Project Overview

This is the developer documentation site for [iDempiere](https://idempiere.github.io), an open-source ERP/CRM/SCM system. Built with Docusaurus 3 and deployed to GitHub Pages.

## Skills

Task-specific instructions live in `.agents/skills/<name>/SKILL.md`. Read the matching skill before starting the task.

| When you are... | Read |
|---|---|
| Writing or updating a New Feature page, a migration note for a breaking change, or moving a page from `in-development` to a version folder | `.agents/skills/idempiere-feature-docs/SKILL.md` |

Instructions for working on the iDempiere core code live in the core repository's own `AGENTS.md`.

`.claude/skills` is a symlink to `.agents/skills`. On Windows, git checks symlinks out as plain files unless they are enabled (Developer Mode, then `git clone -c core.symlinks=true ...`). Without it, automatic skill loading may not work. The table above still points to every skill.

## Git and publishing

- Do not commit or push without the user's confirmation. A push to `main` publishes the site.
- Contributors without write access work on a fork and open a pull request. Do not push to `main` on their behalf.
- Feature documentation commits use the core ticket: `IDEMPIERE-#### Short description`.
- A commit can carry a `Change-Note:` trailer with one sentence for readers. The docs changelog page (`/updates`) shows it. Notes for commits already pushed go in `changelog-notes.yml`.
- Run `npm run build` before committing. It fails on broken internal links (`onBrokenLinks: throw`) and only warns on broken links to `.md` files, so read the warnings too.

## Architecture

### Content Structure

All documentation lives in `docs/`. The sidebar is **auto-generated** from the filesystem (`sidebars.js` uses `autogenerated`), so directory structure and frontmatter control navigation order.

- `docs/basic-installation/` — Installation guides (sidebar position 20)
- `docs/basic-development/` — Plugin development, contributing to core, 2Pack (position 40)
- `docs/new-features/` — Features organized by version (`v13/`, `v14/`, `in-development/`) (position 50)
- `docs/basic-functional/` — End-user guides (position 70)
- `docs/Widgets & Quick Info/` — Widget and Quick Info 2pack documentation

### Category and Ordering

- Each directory can have a `_category_.json` to set its sidebar label, position, and index page description.
- Individual pages use `sidebar_position` in frontmatter to set order within a category.
- The page title is taken from the first `#` heading — do not duplicate it in frontmatter.

### Custom Components

- `src/components/HomepageFeatures/` — Feature cards on the home page
- `src/theme/DocItem/` — Swizzled Docusaurus DocItem (adds Giscus comments)
- `src/theme/SearchBar/` — Swizzled SearchBar (integrates `docusaurus-lunr-search`)

### Plugins

- `docusaurus-lunr-search` — Offline full-text search (no Algolia dependency)
- `@docusaurus/plugin-pwa` — PWA support with offline mode
- `@giscus/react` — GitHub Discussions-based comments on doc pages

## Content Rules

### Do not change content without asking

- Do NOT rewrite, restructure, or rephrase existing content unless explicitly asked.
- Do NOT add sections, paragraphs, or notes unless the user requests it.
- Do NOT delete or move content without confirmation.
- If something looks wrong or incomplete, flag it as a suggestion. Do not fix it silently.

### Do not add things you are not sure about

- If you are unsure whether a fact, feature, or behavior is accurate, say so clearly.
- Do not fill gaps with assumptions. Use a placeholder like `<!-- TODO: verify this -->` and note the uncertainty.
- Do not invent plugin names, configuration keys, API behavior, or version numbers.
- When in doubt, ask.

## Documentation Writing Standards

From `docs/documentation-standards.md`:

- **iDempiere entities**: Capitalize the first letter of named entities (Business Partner, Sales Order, Product).
- **Specific records**: Wrap in quotes ("Azalea Bush" Product, "System" Tenant).
- **Window navigation**: Use `=>` for subtab paths (Sales Order window => Order Line subtab). Use "subtab" (one word) for tabs with Tab Level > 0.
- **Heading hierarchy**: First `#` is the page title (rendered by Docusaurus). All subsequent headings must be `##` or deeper.

### Voice and tone

- Write like a person, not a marketing bot.
- Be direct and factual. Avoid filler phrases.
- Use active voice where possible.
- Short sentences are better than long compound ones.

### Words and phrases to avoid

Do not use the following overused AI-generated terms:

- seamlessly
- streamline / streamlines / streamlined
- leverage (as a verb)
- robust
- utilize (use "use" instead)
- empower / empowers
- cutting-edge
- game-changer
- comprehensive (as filler)
- dive deep / dive into
- delve
- unlock potential
- out of the box (unless referring to a literal software default)
- best-in-class
- revolutionize

### Punctuation

- Do NOT use em dashes (—). Replace with a period, a comma, or a short new sentence.
- Avoid parenthetical asides where a new sentence works better.
- Use plain hyphens (-) for compound adjectives only.

### Lists and structure

- Use numbered lists when order or sequence matters.
- Use bullet points for unordered sets of 3 or more items.
- Do not nest bullets more than one level deep. If sub-points are complex, give them their own section.
- Each bullet should be one idea. Do not pack multiple facts into one bullet.

### Headings

- Use sentence case for headings (e.g., "Basic installation", not "Basic Installation") unless it is a proper noun.
- Keep headings short (under 6 words when possible).
- Do not use a heading for every paragraph.

## What to Do When Unsure

1. Stop. Do not guess.
2. Add a comment: `<!-- TODO: verify — [your question here] -->`
3. Tell the user what is unclear and ask for clarification before proceeding.

## Admonitions

Use Docusaurus admonitions instead of bold text or inline warnings.

Available types:

- `:::note` — extra context that is helpful but not critical
- `:::tip` — a best practice or shortcut worth highlighting
- `:::info` — important background information
- `:::warning` — something the user should be careful about
- `:::danger` — an action that could break something or cause data loss

Do NOT use `:::caution`. It is deprecated in Docusaurus v3 and will be removed in v4. Use `:::warning` instead.

Always leave an empty line after the opening `:::` and before the closing `:::` to avoid Prettier formatting issues.

Example:

:::warning
This step will overwrite existing configuration. Back up your files first.
:::

Do not overuse admonitions. If every other paragraph is a callout, none of them stand out. Use them for genuinely exceptional content, not as a substitute for clear writing.
